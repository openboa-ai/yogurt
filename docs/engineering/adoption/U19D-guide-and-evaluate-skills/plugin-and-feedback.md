# Installed plugin and project-delegated issue reporting

Draft implementation design. Confirm the scoped revision before coding. [Adoption specification](spec.md) · [Execution order](execution.md)

## Installation and version resolution

Deliver one Codex plugin under `plugins/yogurt/`. Its `.codex-plugin/plugin.json` declares its name, version and relative skills directory. The consumer skills for design, implementation, review and feedback load progressively. The maintainer evaluation skill stays with the evaluation tooling. Document first use and rollback from an immutable plugin revision alongside the separately pinned SDK package.

Use one plugin compatibility record that maps each supported pattern catalog format to an SDK release range. Start with format 1 and the exact SDK candidate exercised by the installation suite. Add ranges only as their endpoints are qualified. A skill starts from the active consumer's declared root and its installed SDK. For web, resolve the installed dependency using the consumer's package resolution. For a Native-only project, the integration records the SDK checkout or artifact used to install the generated surface, along with its immutable revision. Accept only the declared installation when its version, revision and catalog format agree. A missing or mismatched installation returns the expected and observed versions, then guides the user to restore a compatible pair.

The plugin reads the installed handbook and pattern lookup rather than embedding a second copy of the design rules. Keep the existing pattern IDs and CLI behavior. Each skill should load only the applicable rules, pattern and renderer support. Include a standalone test for opening a consumer in a host with both the old and candidate plugin available. Demonstrate that adding a newer SDK elsewhere does not redirect the current consumer.

Provide an offline `resolve-sdk.mjs <project-root> <web|native> --lookup <id> [<id> ...]` shortcut for installed pattern and component IDs. Resolve the consumer pin first. Read state rules from the same installed catalog as the pattern lookup. Use the installed component catalog and export map to identify bindings. Report a file or declaration as available only after resolving it inside that SDK. For web, show public imports, export names and the defining declaration paths. Include small declaration modules once within a fixed output budget and give exact paths for the rest. For Native, link to the installed template and the copy command. Preserve the guide and inspection output, and return a useful error for unknown IDs and missing selected files. Test combined decision and receipt lookup, Native templates and rejected pins from a copied plugin and isolated installs. This shortcut reads files and has no model calls, network requests or write effects. Its result describes installed bindings.

Use `--agent-guide` to print a compact section suited to a consumer's `AGENTS.md`. Include repository-relative installed references, stable pattern IDs, and verified binding locations or import names for a small set of baseline controls. A member path and its exposed symbol are distinct from the declaration module that defines its types. Keep the draft local to its target and avoid workstation-specific absolute paths. An incompatible pin fails the same strict checks as `--lookup`. Print only, so the project's existing instructions need no automatic rewrite.

The instruction index names the four consumer skills and their entry conditions. Keep the required rules and compatible bindings visible in the index. Keep design decisions, implementation, renderer verification and feedback steps in their corresponding skills. For review, tie reproducible source findings to a file and line and rendered findings to the observed interaction and state.

When asked what an installation supplies, the design skill inspects the validated pin and reports the installed guide, missing resources and catalog compatibility before selecting an interaction. The inspection result neither changes the pin nor establishes runtime behavior. A project with only an npm pin can report its packaged Native files separately from a declared Native integration. Keep the strict resolver unchanged for tools that require a compatible catalog. Test the inspection against the recorded legacy archive and the compatible package. An untrusted configured path, wrong package, or mismatched lock still fails before returning available resources.

Install each exact plugin revision into a disposable Codex profile through its own marketplace. A changed plugin receives a new version so discovery and rollback can distinguish the installed bytes. Hold the SDK pin fixed when changing only the plugin. In a fresh session, verify discovery and references through files in the installed cache. Upgrade one fixture profile while a second stays on the preceding plugin, then roll back the first and observe both profiles and their SDK locks again. The test uses local marketplace snapshots and leaves the operator's profile untouched.

## Project routing and authorization

Place a declarative issue routing section under the existing `yogurt.config.json`. It can name the project tracker and the shared-kit tracker. During draft preparation the project may also omit both destinations. Consume write delegation from trusted host configuration tied to the exact project, canonical target repository and `create_issue` operation. A repository file may describe routing. A file or instruction in the inspected checkout cannot authorize writes. The broker verifies project identity, repository identity, configured actor and operation immediately before creation. Use the host's GitHub connector credentials.

Route a reproduced defect to the layer that owns the failed contract. Use a portable draft when the issue owner is uncertain, the request calls for a draft, the host has no matching grant, or the connector cannot read the configured tracker. The draft includes the affected pin and renderer, stable public ID, expected and observed states, reproducible steps, impact and a checkable acceptance condition. Use shareable fixture data. A deployment may grant only one destination.

## Search, create and reconcile

1. Resolve the candidate report and destination. Search open and closed issues within that repository for the relevant public ID, renderer and symptom. Compare bodies for matching behavior. Return the existing canonical issue when it matches. For a recurrence of a closed defect, identify the previous issue and the newly affected revision before treating it as a new report.
2. Build a report identity from repository identity, renderer, public ID and reproduced failure signature. Include the prior closed issue and new affected revision for an explicitly verified recurrence. Record the identity in a machine-readable marker in the issue body. A rewritten title does not change the identity.
3. Under a lock in the host's durable reporting store, read the report state and perform a final lookup before creation. Persist a pending attempt before calling the connector. Every worker allowed to create for this project must share the same reporting store. Where coordination is unavailable, return a draft. After a definitive response, retain the confirmed issue number and URL or an actionable definitive error.
4. On timeout, transport loss or interruption after the pending record, look for the exact marker in the authorized repository. Update the durable record if found. If the write outcome remains ambiguous, retain pending state and report what was checked. A subsequent invocation resumes reconciliation. A definite rejected write can be submitted again only after its cause is resolved and reauthorization and duplicate search pass.

The skill owns classification and report preparation. The host broker owns authority, durable coordination and the write. A denied or ambiguous result returns a draft and status. Existing reports can be returned by URL under read access. This first scope emits new issues under the selected delegation. Editing or commenting requires its own authorization and design.

## Acceptance

| ID | Setup and action | Required observation |
| --- | --- | --- |
| PF-1 | Open a fresh consumer with only the pinned plugin and SDK, then replace just one pin with an incompatible release. | Correct skills and local references load with the compatible pair. The incompatible pair reports the mismatched data, and restoring the pair restores the workflow. |
| PF-2 | Provide a project-only permission error and a reproducible defect in a shared dialog in separate fixtures. | The former routes to the consumer. The latter routes to the kit tracker. Both outputs retain the source of evidence and avoid restricted user data. |
| PF-3 | Give the agent an editable routing file whose destination is outside the trusted grant, then repeat at the trusted destination without a grant. | Both runs return usable drafts with zero writes. |
| PF-4 | Seed a matching issue with a differently worded title in the destination and a similarly titled but unrelated issue elsewhere. | The matching body and repository determine the returned issue. Zero writes occur. |
| PF-5 | Issue the same request twice concurrently. On the first create, have the tracker persist an issue and drop the response. | The ledger receives at most one create. A replay determines the result from the exact marker and reports the existing canonical issue. |
| PF-6 | Drop the response and keep the pending effect invisible to the next lookup. Interrupt the agent and reopen the project before retrying. | State survives restart. The host reports a pending result and does not make a second write while that outcome is unknown. |

Use a simulated tracker with controllable response loss, visibility and call logs. Follow the [evaluation protocol](evaluation.md) for agent-side observations.
