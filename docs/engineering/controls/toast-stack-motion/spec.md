# Toast stack presentation

Status: reviewed implementation scope under the owner-selected motion-led component foundation replacement. This Web presentation does not establish Native behavior or visual approval. The reviewed `toast-exit` specification remains the authority for removal, focus transfer, cleanup and host ownership.

## Intent and boundary

Let products present several notifications as a compact layered stack that expands into readable separate notices. Apply this behavior through the ordinary `ToastStack` export and its editable entry so the gallery does not own a second notification implementation. Reuse the existing neutral toast surface, text and dismissal control, motion roles and the host-provided `items`, `onDismiss` and `label`.

The host retains the full ordered list, stable unique IDs, messages and removal decisions. Expanding or collapsing only changes presentation: it cannot add, remove, reorder, acknowledge or dismiss an item. A dismissal requests an action once and an item exits only after its ID is removed by the host, as specified in `toast-exit`. Do not add a notification manager, persistence, an automatic dismissal policy or a limit that discards host items.

## Presentation contract

- Preserve the current vertically listed presentation as the default for existing callers. An explicitly selected stacked presentation is opt-in. Its compact state is the initial state unless a caller explicitly requests another state through the reviewed public contract. A caller must not need to implement a separate animation to use it.
- In compact state, show the foremost active notice and a restrained depth cue for additional items. Make the number of additional notices understandable without relying on scale, color or hover. Do not limit the underlying list to the number of visually distinct layers.
- When two or more notices are active, provide a visible, named button to expand and collapse them. The button exposes `aria-expanded` and controls the notification collection. It remains usable with pointer, touch and keyboard; hover alone is not the only way to reveal notices. A single notice does not need a redundant expansion control.
- In expanded state, show active items in host order with a consistent gap; the full text and dismissal action of each item remain reachable. On a narrow or height-constrained host, allow the list to scroll rather than clip content, overlap controls or enlarge the page. Real message height is authoritative: the sample's short single-line measurements must not truncate long or enlarged text.
- In compact state, each active notification must retain the existing announcement contract. Keyboard focus must never land on a visually obscured action. If active notices remain in the accessibility tree, focus entering an obscured notice must reveal it immediately and keep a visible focus indication. If a design instead makes those notices inert, it must supply an equivalent one-time live announcement without duplicating, suppressing or replaying notifications; this mechanism requires explicit review before implementation.
- Keep the collapse/expand visual transition distinct from each notice's arrival and host-confirmed exit. Use nested presentation layers if required so a swipe or removal cannot overwrite the stack transform. Interruptions and direction changes start from the current presentation without a jump. A removed entry must not reserve an incorrect permanent slot; returning an ID while it exits must cancel its stale cleanup and show exactly one current entry.
- Under reduced motion, apply the same final layouts immediately. Changing the preference during a transition settles without changing host data or losing focus. A normal-to-forced-colors transition must retain readable messages, the expand state, and visible focus without introducing an ordinary decorative outline.
- Swipe-to-dismiss is not part of this presentation slice. Retain the normal dismiss action and the existing exit contract; any later gesture must have a separate cancellation, pointer and host-authorization contract.

## Verification and completion

1. Render the ordinary export and an installed editable entry with zero, one, two, three and more than three notices. Confirm the default list remains compatible and the stacked presentation does not drop or reorder host items.
2. At 320 and 1440 CSS pixels in light and dark, compare compact, expanded and interrupted frames with short, long, multiline and enlarged text. Verify container resizing and height constraints do not clip messages, focus, dismiss controls or the next layout. Record observed visual results separately from geometry assertions.
3. Exercise the toggle and every dismissal by keyboard, pointer and touch. Confirm accessible name and expanded state, discoverability without hover, and focus visibility when entering a notice that was visually behind another. Check actual announcements for newly added and updated messages while compact and expanded, including multiple items supplied together; no active message may be silently lost or announced twice solely due to expansion.
4. Confirm a host that ignores a dismissal request keeps the item actionable. Exercise removal during expansion, simultaneous removals, rapid expansion reversal, and removing then immediately re-adding the same ID with changed text. Verify latest host content and action win, focus is not stolen, and old timers cannot remove a current item.
5. Test reduced motion before and during movement, forced colors, unmount during movement, and repeated mount/unmount. Confirm the static fallback preserves all content and behavior and no timers, listeners or animation work remain after removal.
6. Verify the sample uses the public component rather than a separate stack and re-run existing `ToastStack` exit, installed-consumer and catalog checks. Keep the change incomplete until its actual visual/motion review and any applicable renderer-specific support are recorded.
