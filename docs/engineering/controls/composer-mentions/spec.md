# Optional mentions in the composer

Status: reviewed Web implementation scope. The owner selected an opt-in Composer integration, with collapsed-selection gating in Composer and the existing standalone range behavior preserved. This review does not establish implementation, Native or visual support. The existing `composer-motion` and `motion-patterns` specifications remain authoritative for the current components.

## Intent and boundary

Allow a caller to compose a message with the existing mention interaction without building a second editor, duplicating the popup behavior or changing the meaning of a message. Reuse a single maintained mention controller and list presentation in the standalone mention entry and, when explicitly enabled, in `Composer`. Share the underlying textarea and its measurement only where their existing contracts are preserved. A caller that does not enable mentions sees the same public `Composer` behavior and markup semantics it has today.

The host owns the draft string, the available people, the current suggestion dataset, attachments, tool effects, send and stop requests, and all resulting work. Typing, highlighting, dismissing or animating never sends a message, selects a person externally, fetches a list or starts a service action. The component requests a draft change through the existing controlled-value callback; the host may accept, delay, reject or replace that request. A displayed label alone does not establish a durable identity or permission. Do not add an identity callback in this scope.

Preserve current public IDs, import paths, props, callback signatures and accessible labels for `Composer`, `PromptBox` and `MentionPicker`. Do not require a host to install or adopt mentions. Add only the optional `Composer` prop `mentionPeople?: readonly { id: string; label: string }[]`: omitted means mentions are disabled; an empty list enables the behavior with no available matches. This is a synchronous host-supplied list, not a new search or ID callback. This scope does not add an agent, network client, global search cache, editor document model, new product policy, automatic send or Native support.

## Existing editor contracts

- `Composer` keeps its controlled `value`/`onValueChange`, trimmed text and attachment-ID `onSend` payload, upload gating, pending/stop behavior, tool and attachment callbacks, labels, errors, two-row minimum and manual vertical resize. Its textarea currently treats Enter and Shift+Enter as native text editing; adding mentions cannot make Enter submit.
- `PromptBox` keeps its one-row compact layout, Enter-to-submit, Shift+Enter newline, IME guard, busy state and optional cancellation. This proposal does not enable mentions in `PromptBox`; extracting a shared editor cannot change its keyboard contract.
- `MentionPicker` keeps its controlled string, supplied `{id, label}` people list, label, text-change callback, matching and single-token replacement contract. Its two-row editor, hint, keyboard, pointer, popup motion and reduced-motion behavior remain available through the existing public entry. No callback for an ID exists today, and the existing string callback must not acquire an implicit send or host action.
- The editor remains a real textarea with the existing description/error relationships, selection, form semantics and readable scrollable content. Any shared ref must compose rather than replace the internal editor and caller handlers. An absent measurement API must not block text entry or its actions.

## Interaction and state contract

- The opt-in controller receives the current host-supplied candidate data and computes the candidate token from the actual focused textarea's current selection and current controlled text. It maintains only presentation state: open or dismissed, the active candidate and any pending caret restoration. Reuse the existing mention token and replacement rules where they apply; retain surrounding text and suffix exactly.
- During an active IME composition, do not select a candidate, replace text, submit, or reinterpret composition Enter as a mention or message action. Recompute from the committed editor state after composition ends. Never split a surrogate pair: DOM textarea offsets are UTF-16 offsets, and any conversion or clipping must preserve the browser's valid selection boundaries.
- For an opt-in `Composer`, a noncollapsed selection suppresses candidate presentation and selection until the range is collapsed, preserving all selected text. Keep the existing standalone `MentionPicker` range-selection behavior unchanged through the shared extraction. Test both behaviors independently.
- When a valid mention list is open, unmodified Up/Down moves among current candidates, Enter chooses the active valid candidate once, and Escape dismisses the list without changing the draft. In opt-in Composer, respect modifiers so Shift+Enter remains a newline; preserve the standalone picker's existing modifier-key behavior. Respect an already-prevented event. Outside an open list, each entry retains its original native editing or submit behavior. Opening and moving the highlight cannot call the selection or send callbacks.
- Matching and active items must remain consistent with the current token and candidate dataset. A change in the caret, current token, host value or list must not leave an active reference to an obsolete or removed candidate. Disabled candidates, if a future reviewed API provides them, cannot be activated. No disabled option is implied by the current `MentionPicker` people type.
- Escape dismisses only the current interaction; a subsequent meaningful edit or token change can open a new one. Blur, unmount, composition start and an incompatible host value invalidate stale presentation and pending selection work. User movement of the caret or selection after proposing a replacement invalidates that proposal's caret restoration, without undoing an eventual host-controlled text update.
- Restore the proposed caret at most once after the host commits the exact proposed replacement, and only if the same textarea remains focused and no later edit, caret move, blur or conflicting value has invalidated it. Host rejection cannot be presented as a committed selection; delayed acceptance cannot steal focus or apply an old caret to unrelated content. A later identical string after an intervening conflicting value is not proof that an old proposal was accepted.
- Consume only the synchronously supplied list and perform no fetch. Add no query-notification or asynchronous search API in this scope. Recompute the active item against each current host list; do not infer identity from list order or display labels.

## Presentation and accessibility

Use the current shared surfaces, typography, spacing, motion roles and the existing mention list rather than adding a separate theme or ordinary outline. Keep the input, status, popup and actions within their host at 320px and wider; long drafts and candidate labels remain readable. A list may render outside a clipping ancestor only through an explicitly supported positioning and focus strategy.

Expose the editor's existing label and help/error descriptions. When suggestions are available, expose their relationship, open state and active option to assistive technology using semantics valid for the actual textarea and list; never point to an absent, hidden, removed or disabled option. Pointer and touch selection must not accidentally blur the editor before the action resolves, and keyboard users must retain a visible focus cue. Duplicate visible labels must not select an unintended candidate. Use host IDs as stable list keys; their use must not silently alter the message format.

Use the existing popup and marker motion, including rapid retargeting and interruption. Reduced motion settles the same list, active option and draft immediately; forced colors retain a readable focus and selected state. Unmount and dismissal cancel observers, scheduled animation and pending caret work. Verify actual supported renderers individually; generated tokens alone do not establish Native behavior.

## Acceptance evidence

1. In ordinary installed Web consumers, compare unchanged `Composer`, `PromptBox` and `MentionPicker` against their current public contracts before exercising the opt-in. Verify export and editable entry, no new required props, no unexpected effect and one host callback per explicit action.
2. Type mentions at the start, middle and end of a multiline draft, including two successive mentions and a suffix. Exercise collapsed and noncollapsed selection according to the reviewed rule, a duplicate label with distinct IDs, cursor movement, emoji and non-Latin input. Confirm that no surrounding text disappears and the committed caret is correct.
3. Exercise immediate acceptance, deferred acceptance, rejection, conflicting external replacement, new input, caret or selection movement, blur, unmount and a later coincidentally identical value. Confirm no stale caret restoration, focus stealing, duplicate text change, send or service effect. Replace the synchronous candidate list while open and confirm removed entries cannot be selected.
4. Exercise IME start/update/end, IME Enter, Enter, Shift+Enter, arrows, Escape, pointer and touch. Confirm the standalone picker chooses once, an open mention in the opt-in composer does not submit, ordinary composer Enter remains a newline, and PromptBox Enter retains its existing submit policy.
5. Check actual accessibility tree relationships, keyboard focus, long candidate names, empty and changing lists, narrow and wide screens in both appearances, reduced motion and forced colors. Compare rest, opening, navigation, dismissal and rapid reversal frames against the current shared components, including near viewport edges.
6. Build and test the actual package and editable entries in Vite and Next.js. Record browser, environment, visual and motion evidence separately from any Native renderer evidence. Do not call the scope complete until all agreed acceptance cases and the requested interactive owner preview are observed.
